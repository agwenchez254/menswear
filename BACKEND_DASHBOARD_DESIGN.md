# Jabali Backend and Admin Dashboard: Design Document

Status: Draft v1 · Stack: NestJS, PostgreSQL, Redis, React, shadcn/ui · Date: 2026-10-14

## 1. Goals and non-goals

**Goals**
- Replace the hard-coded catalogue in `src/data/products.ts` with an API-backed catalogue the team can edit without a deploy.
- Give staff a dashboard to manage products (with colour and size variants, per-colour photos), promotions, orders, and site content (hero, banners, testimonials, category tiles).
- Move cart totals, promo validation, delivery fees and stock checks to the server, so prices can't be tampered with in the browser.
- Scale from one shop to thousands of SKUs and heavy traffic during campaigns without a rewrite.

**Non-goals (v1)**
- Multi-vendor marketplace, multi-currency (KES only), native mobile apps, warehouse management.

## 2. System overview

```
 Storefront (Vite + React)      Admin Dashboard (React + shadcn)
          │  public REST             │  admin REST (JWT + RBAC)
          └──────────────┬───────────┘
                         ▼
                 API Gateway / Nginx  (TLS, rate limit, gzip)
                         ▼
        ┌──────────── NestJS API (stateless, N replicas) ────────────┐
        │  modules: auth, users, catalogue, inventory, promotions,   │
        │  cart, orders, payments, content, media, audit, search     │
        └───┬───────────┬────────────┬────────────┬─────────────────┘
            ▼           ▼            ▼            ▼
       PostgreSQL     Redis      Object store   Queue workers (BullMQ)
      (primary +    (cache,      (S3 / R2 +     emails, M-Pesa callbacks,
       read replica) sessions,    CDN)          image resize, search sync,
                     rate limit)                 stock reservations expiry
```

Key decisions:
- **Modular monolith first.** One NestJS app with strict module boundaries (each module owns its tables and exposes a service interface). Modules can be split into services later if one needs to scale independently (likely `orders/payments` first). This avoids early microservice overhead.
- **PostgreSQL** as the system of record (relational integrity for orders, stock, promotions). JSONB only for flexible content blocks.
- **Redis** for catalogue cache, rate limiting, idempotency keys, and BullMQ queues.
- **Stateless API** so it scales horizontally behind a load balancer.
- **Two API surfaces** from the same codebase: `/api/v1/store/*` (public, cached, read-heavy) and `/api/v1/admin/*` (authenticated, RBAC-protected, write-heavy).

## 3. Tech choices

| Concern | Choice | Reason |
|---|---|---|
| API framework | NestJS 11 (TypeScript) | Modules, DI, guards and pipes fit a growing team |
| ORM | Prisma (or TypeORM if the team prefers) | Typed queries and migrations |
| Database | PostgreSQL 16 | Transactions, constraints, JSONB, full-text search |
| Cache / queue | Redis 7 + BullMQ | Caching, rate limit, background jobs |
| Search | Postgres FTS + `pg_trgm` in v1; Meilisearch when the catalogue passes ~20k SKUs | Start simple |
| Media | S3-compatible bucket + CDN, `sharp` workers for resizing | Offloads image traffic |
| Auth | JWT access (15 min) + rotating refresh token (httpOnly cookie) | Standard, revocable |
| Validation | `class-validator` DTOs + shared Zod schemas for the dashboard | Fail early |
| API contract | OpenAPI generated by `@nestjs/swagger`; typed client generated for the dashboard and storefront | One source of truth |
| Dashboard | React 19, Vite, React Router, TanStack Query, TanStack Table, react-hook-form + Zod, shadcn/ui (Radix + Tailwind v4) | Matches the storefront stack |
| Observability | pino logs, OpenTelemetry traces, Sentry, health endpoints | Debuggable in production |
| CI/CD | GitHub Actions, Docker, migrations run as a release step | Repeatable deploys |

## 4. Data model

Core tables (all have `id uuid`, `created_at`, `updated_at`; soft delete via `deleted_at` where noted).

**Catalogue**
- `categories` (id, gender, slug, label, tagline, image_id, sort_order, parent_id)
- `products` (id, slug, name, gender, category_id, blurb, base_price, compare_at_price, status `draft|active|archived`, is_new, is_bestseller, rating_avg, sold_count, search_vector) · soft delete
- `colours` (id, name, hex): shared swatches
- `product_colours` (product_id, colour_id, sort_order): which colours a product comes in
- `product_images` (id, product_id, colour_id nullable, media_id, position): **per-colour galleries**; a null colour means shared. The storefront shows the selected colour's images, falling back to shared ones.
- `variants` (id, product_id, colour_id, size, sku unique, price_override nullable, barcode)
- `inventory` (variant_id PK, on_hand, reserved, low_stock_threshold): `available = on_hand - reserved`
- `inventory_movements` (id, variant_id, delta, reason `sale|restock|adjustment|return`, ref, actor_id): append-only audit trail of stock

**Promotions**
- `promotions` (id, name, code nullable, type `percent|fixed|free_delivery|bogo`, value, status, starts_at, ends_at, usage_limit, per_customer_limit, min_subtotal, stackable bool, priority)
- `promotion_targets` (promotion_id, target_type `all|category|product|collection`, target_id): what it applies to
- `promotion_redemptions` (id, promotion_id, order_id, customer_ref, amount)

**Orders**
- `customers` (id, name, phone, email nullable): guest checkout keyed by phone
- `orders` (id, number, customer_id, status `pending|paid|packed|shipped|delivered|cancelled|refunded`, method `delivery|pickup`, subtotal, discount, delivery_fee, total, payment_method, county, address, eta, idempotency_key unique)
- `order_lines` (id, order_id, variant_id, name_snapshot, colour_snapshot, size, unit_price, qty, gift jsonb)
- `payments` (id, order_id, provider `mpesa|airtel|card|cod`, status, amount, provider_ref, raw jsonb)
- `order_events` (id, order_id, type, actor_id, note): timeline

Prices and names are **snapshotted** on the order line so later edits never change past orders.

**Delivery**
- `delivery_zones` (id, name, counties text[], fee, eta_days, free_over nullable)

**Content (CMS)**
- `content_blocks` (id, key, kind `hero|banner|testimonial_set|category_tiles|rich_text|faq|gift_promo`, gender nullable, data jsonb, status `draft|published`, publish_at, unpublish_at, version)
- `content_block_versions`: history for rollback
- `testimonials` (id, name, location, quote, avatar_media_id nullable, rating, gender, is_published, sort_order)
- `pages` (id, slug, title, blocks jsonb, status): policies, about, size guide
- `media` (id, key, url, mime, width, height, bytes, alt, uploaded_by)
- `site_settings` (key, value jsonb): free-delivery threshold, WhatsApp number, announcement bar

**Access and audit**
- `staff_users` (id, name, email unique, password_hash (argon2), role_id, status, last_login_at)
- `roles` / `role_permissions` (permission strings such as `product:write`)
- `audit_log` (id, actor_id, action, entity, entity_id, before jsonb, after jsonb, ip, at): written by an interceptor on every admin write

Indexes: `products(status, category_id, gender)`, `variants(sku)`, GIN on `products.search_vector`, `orders(status, created_at)`, `promotions(code)`, `promotions(status, starts_at, ends_at)`.

## 5. NestJS module layout

```
apps/api/src
  main.ts
  app.module.ts
  common/            guards, decorators, filters, interceptors (audit, cache), pagination, idempotency
  config/            typed env config (zod-validated)
  auth/              login, refresh, logout, JWT strategy, RolesGuard / PermissionsGuard
  staff/             staff users and roles
  catalogue/         products, categories, colours, variants, images   (store + admin controllers)
  inventory/         stock levels, reservations, movements
  promotions/        CRUD and the pricing/discount engine
  cart/              server-side price quote (stateless): POST /store/cart/quote
  orders/            checkout, status transitions, timeline, exports
  payments/          provider adapters (MpesaDaraja, Airtel, Card) + webhooks
  delivery/          zones and fee calculation
  content/           blocks, testimonials, pages, settings, scheduling
  media/             presigned uploads, processing jobs
  search/            query + indexing
  analytics/         dashboard aggregates
  audit/             audit log reads
  health/            liveness / readiness
```

Each module follows `controller → service → repository`, with DTOs for input and response mappers for output. Cross-module calls go through exported services only.

## 6. API surface (v1)

**Public storefront (cacheable, no auth)**
- `GET /store/categories?gender=`
- `GET /store/products?gender=&category=&colour=&size=&min=&max=&sort=&q=&cursor=`
- `GET /store/products/:slug` (includes colours, per-colour images, variant availability)
- `GET /store/content/:key` and `GET /store/home?gender=` (resolved published blocks and testimonials in one call)
- `GET /store/delivery/quote?county=&subtotal=`
- `POST /store/cart/quote` (lines + promo code → authoritative totals, discount breakdown, stock warnings)
- `POST /store/orders` (requires `Idempotency-Key` header; reserves stock, creates order and payment intent)
- `POST /store/payments/mpesa/stk-push`, `POST /webhooks/mpesa` (signed, idempotent)
- `GET /store/orders/:number?phone=` (order tracking)

**Admin (JWT + permission guard)**
- `auth`: `POST /admin/auth/login | refresh | logout`, `GET /admin/me`
- Products: `GET/POST /admin/products`, `GET/PATCH/DELETE /admin/products/:id`, `POST /admin/products/:id/variants`, `PUT /admin/products/:id/images` (reorder and assign colour), bulk `PATCH /admin/products/bulk` (status, price %, category), CSV `import` and `export`
- Inventory: `GET /admin/inventory`, `POST /admin/inventory/adjust`, low-stock list
- Promotions: CRUD, `POST /admin/promotions/:id/activate | pause`, `GET /admin/promotions/:id/redemptions`
- Orders: list and filter, `GET /admin/orders/:id`, `POST /admin/orders/:id/transition`, refund, export
- Content: blocks CRUD with draft, preview, publish, schedule, version history and rollback; testimonials CRUD; pages; settings
- Media: `POST /admin/media/presign`, `POST /admin/media/:id/confirm`, list and delete
- Staff and roles, audit log, analytics (`/admin/analytics/summary|sales|top-products`)

Conventions: cursor pagination, `?fields=` where useful, RFC 7807 problem+json errors, `ETag` on store reads, versioned under `/api/v1`.

## 7. Key flows

**Pricing and promotions engine (server-side, pure function + tests)**
1. Load variants and base prices for the cart lines.
2. Fetch active promotions (cached 60 s) matching code or automatic ones, in window, with usage left.
3. Evaluate by `priority`; apply targets (product, category, all); respect `stackable`, `min_subtotal`, per-customer limits.
4. Add delivery fee from the zone, apply `free_delivery` promos and the free-over threshold.
5. Return a line-by-line breakdown. The same function runs at quote time and at order creation, so totals can't drift.

**Checkout and stock**
1. Client posts lines with `Idempotency-Key`.
2. In one DB transaction: re-price, `SELECT … FOR UPDATE` the inventory rows, check `available`, increment `reserved`, create `orders`, `order_lines`, `payments(pending)`.
3. Trigger the M-Pesa STK push. Reservation expires via a delayed BullMQ job (for example 15 min) that releases stock if unpaid.
4. Webhook marks payment paid, converts reservation to a sale (`on_hand -= qty`, `reserved -= qty`), writes an `inventory_movements` row, and enqueues the confirmation message.
5. Cash on delivery follows the same path but starts as `pending` until dispatch.

**Content publishing**
Editor edits a block (draft) → preview URL renders the draft via a signed token → publish bumps `version`, stores the old one in `content_block_versions`, invalidates the Redis cache key and sends a CDN purge. Scheduled blocks are published by a repeatable job at `publish_at`.

**Media**
Dashboard requests a presigned PUT URL, uploads straight to object storage, calls confirm; a worker generates responsive sizes (400/800/1400 webp/avif) and stores dimensions. The storefront uses the CDN URLs.

## 8. Security

- Argon2id password hashes, login rate limiting and lockout, optional TOTP 2FA for owners.
- RBAC via permission strings. Default roles: `owner` (all), `manager` (catalogue, promotions, orders, content), `content_editor` (content, media, testimonials), `fulfilment` (orders, inventory), `viewer` (read-only).
- Refresh tokens rotate and are stored hashed; reuse detection revokes the family.
- Helmet, strict CORS allow-lists per surface, CSRF protection for cookie-based refresh, input validation on all DTOs (`whitelist` + `forbidNonWhitelisted`).
- Webhook signature verification and IP allow-listing for payment providers; idempotent handlers.
- Uploads: MIME and size limits, signed URLs, no public write access to the bucket.
- Secrets in a secret manager, never in the repo. Admin actions are audit-logged. PII (phone, address) minimised and encrypted at rest at the disk level.
- Dependency scanning and a regular backup and restore drill.

## 9. Scalability and performance

- **Read path:** storefront endpoints are cached in Redis (60 s to 5 min, tag-invalidated on admin writes) and behind a CDN with `stale-while-revalidate`. The catalogue is mostly static, so expect a very high hit rate.
- **Write path:** orders are the only hot writes. Keep transactions short, lock per-variant rows in a consistent order to avoid deadlocks, and use the idempotency key to make retries safe.
- **Database:** pooled connections (PgBouncer), a read replica for dashboard analytics and reports, partition `audit_log` and `inventory_movements` by month once large, add pre-aggregated `daily_sales` tables for dashboard charts.
- **Async work** (messages, image processing, search sync, report exports) runs in BullMQ workers that scale separately from the API.
- **Horizontal scaling:** the API is stateless; run 2+ replicas behind a load balancer with health-based autoscaling. Workers are a separate deployment.
- **Search:** Postgres FTS now; swap behind a `SearchService` interface for Meilisearch or OpenSearch without touching controllers.
- **Targets:** p95 storefront read under 150 ms (cached), p95 checkout under 800 ms (excluding provider), 99.9% availability, zero oversells.
- **Load testing** with k6 before launches and promotions.

## 10. Admin dashboard (React + shadcn/ui)

**Structure (`apps/admin`)**
```
src/
  app/            router, providers (QueryClient, Auth, Theme), layouts
  components/ui/  shadcn primitives (button, input, dialog, sheet, table, tabs, form, select, popover, calendar, badge, toast/sonner, dropdown-menu, command, skeleton, alert-dialog, chart)
  components/     DataTable, PageHeader, ConfirmDialog, ImageUploader, ColourPicker, StatusBadge, RichTextEditor, EmptyState, PermissionGate
  features/
    auth/  dashboard/  products/  inventory/  promotions/  orders/  content/  media/  customers/  staff/  settings/  audit/
  lib/            api client (generated from OpenAPI), query keys, formatters (KES), zod schemas, hooks (useDebounce, usePermission)
```

**Layout:** collapsible sidebar (shadcn `sidebar`) with sections Overview, Catalogue, Orders, Marketing, Content, Settings; top bar with global search (`command`), theme toggle and user menu. Fully responsive: the sidebar becomes a sheet on mobile, and data tables get a card view on small screens.

**Screens**
1. **Overview:** sales today/week/month, orders by status, revenue chart, top products, low-stock alerts, recent orders. (`chart` + `card`)
2. **Products:** server-side paginated `DataTable` (search, filters for category, gender, status, stock; bulk actions). The editor is a tabbed form: *Details* (name, slug, blurb, category, price, compare-at, flags), *Colours and variants* (add swatches, generate size grid, SKU, stock per variant), *Images* (drag-and-drop gallery **per colour**, reorder, alt text), *SEO*, with draft/active/archived status and an unsaved-changes guard.
3. **Inventory:** stock by variant, inline adjust with reason, low-stock filter, movement history, CSV import.
4. **Promotions:** list with status chips (scheduled, live, expired). The create/edit wizard sets type and value, target (all, categories, products), schedule (date-range picker), limits, stacking, and shows a **live preview** of the effect on a sample cart. Redemption stats per promotion.
5. **Orders:** filterable table, order detail with line items, payment status, timeline, status transitions, print packing slip (hides prices for gift orders), refund, CSV export.
6. **Content:** block library for the site: *Hero*, *Banners*, *Category tiles*, *Gift promo*, *FAQ*, pages. Each block has a form editor and a side-by-side **preview**, draft/publish/schedule, version history with rollback. **Testimonials** manager: add/edit/reorder, upload an avatar, publish toggle, with the same data driving the storefront carousel.
7. **Media library:** grid with upload, search, alt text, usage references, bulk delete (blocked while in use).
8. **Settings:** delivery zones and fees, free-delivery threshold, payment methods, WhatsApp number, announcement bar.
9. **Staff and roles, Audit log:** owner-only.

**Frontend practices:** TanStack Query for server state with optimistic updates on toggles and reorders; react-hook-form + Zod (schemas shared with the API where possible); `PermissionGate` hides actions the role can't use (the API still enforces); route-level code splitting; accessible by default via shadcn/Radix; consistent theming through the same design tokens as the storefront.

## 11. Storefront integration plan

1. Add a typed API client; replace `src/data/products.ts` reads with TanStack Query hooks calling `/store/*`.
2. Server returns `colourImages`, so the product page swaps the gallery when a colour is selected (the current static `colorImages` field in the prototype is the same shape).
3. Cart stays in the browser, but totals, promo codes and delivery fees come from `POST /store/cart/quote`; checkout calls `POST /store/orders`.
4. Home page sections (hero, tiles, testimonials, gift promo) read from `/store/home`, with the current copy used as a fallback if the API is unreachable.
5. Delivery zones and the free-delivery threshold move from `src/data/delivery.ts` to the API.

## 12. Deployment and environments

- Environments: local (Docker Compose: Postgres, Redis, MinIO, API, admin), staging, production.
- Containers for API, worker, admin (static, served from CDN) and storefront. Run on a managed container platform (ECS, Fly, Render or Kubernetes) with managed Postgres and Redis.
- Database migrations run in CI/CD before the new version takes traffic; backwards-compatible (expand then contract) so rollbacks are safe.
- Nightly automated backups with point-in-time recovery, restore tested quarterly.
- Feature flags for risky releases; blue/green or rolling deploys with health checks.

## 13. Testing strategy

- Unit tests for the pricing and promotion engine (table-driven, including stacking and expiry edge cases), inventory reservation logic and status transitions.
- Integration tests with Testcontainers (real Postgres and Redis) covering checkout concurrency (two buyers, last item) and webhook idempotency.
- E2E API tests (supertest), contract tests from the OpenAPI spec, Playwright smoke tests for dashboard flows (create product, publish promotion, edit content).
- Load tests (k6) on catalogue reads and checkout.

## 15. Risks and open questions

- **Payments:** Daraja credentials, callback reliability and reconciliation for missed callbacks (mitigation: periodic status query job).
- **Photography:** per-colour galleries need real product photos for each colour. Stock images can't guarantee this, so the dashboard should warn when a colour has no images.
- **Search scale:** decide when to move off Postgres FTS (suggested trigger: slow queries or more than 20k SKUs).
- **Tenancy:** confirm this is a single shop. Multi-store would add a `store_id` to most tables, so decide before building the schema.
- **Compliance:** data protection (Kenya DPA) for customer phone and address data, and a retention policy for orders and audit logs.
- **Ownership of content:** who may publish live content (approval workflow vs. direct publish for `content_editor`).
